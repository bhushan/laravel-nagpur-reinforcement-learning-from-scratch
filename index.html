Act 1 · Test-driven development

TDD is a loop with a judge in it.

  • Red. Write a test for behaviour that does not exist yet. Watch it fail.
  • Green. Write the smallest code that makes it pass. Nothing clever.
  • Refactor. Clean it up. The test tells you if you broke anything.

The test comes first, so it cannot be bent to fit the code.

Watch one lap

Put a product in a cart, test first.

Real test names from the project we meet in the last act.

0:50. Everyone in this room has done this, so go fast. Red: write the test, watch it fail. Green: smallest code to pass. Refactor: tidy up while the tests guard you.

The line to land: the test comes first, so it cannot be bent to fit the code. That independence is what makes the verdict trustworthy. Hold that thought, it returns in the reward function.

Point at the dot circling the loop. It never stops. Every new requirement starts another lap.

2:10, seven steps, about 18 seconds each. Press forward once per beat and narrate it.

1. The test exists before any code. 2. Run it: red, a 404 because no route exists. 3. Smallest code that could pass. 4. Green. 5. New requirement, new failing test: repeat adds should merge, so this time the naive code fails with two lines instead of one. 6. Fix, green. 7. Refactor with the tests as a net.

Say clearly at step 4: we never explained to the test how the code works. It only judges. Remember this exact test, it is the reward later.

Do not type anything live. The animation is the demo.

Why it works

Three properties make a test a good judge.

Objective

Pass or fail.

No opinions, no mood, no "looks fine to me".

Automatic

Seconds, no human.

Nobody has to read the code to know the verdict.

Repeatable

Same code, same verdict.

Run it a thousand times and it never changes its mind.

Keep these three words

A judge that is objective, automatic and repeatable can score a million attempts without getting tired. That is the entire requirement for a reward.

1:00. Slow down on each card, one sentence each.

Objective: the test does not care about style or effort. Automatic: it runs without a human. Repeatable: no flakiness, or the signal is noise.

Then the bridge sentence: a judge with these three properties can score a million attempts without getting tired. In reinforcement learning we call what the judge hands back a reward. Write the three words in your head: objective, automatic, repeatable.

Aside if asked: flaky tests are poison for exactly this reason. We will see a version of that when a model learns to cheat the judge.

The loop

Act, get judged, adjust, repeat.

Nobody says which action was right. The agent only learns that some actions paid more than others.

1:20. Reveal one row per press and say the middle column out loud. This single table is the translation key for the rest of the talk.

Developer is the agent. Ticket plus codebase is the state. Writing code is the action. The test suite is the environment. Red or green is the reward. Fixing after a failure is the policy update, which is the learning itself.

The only real difference: your fix lives in your head. The model's fix is a small change to millions of numbers called weights. We will open that up later.

1:10. Two boxes. The agent acts, the environment responds with a new state and a reward, and the agent adjusts so the next action earns more.

Map it to the cart: the agent is the model, the environment is the shop app plus the hidden tests. The action is the code it writes. The reward is 1.0 if every test passes, else 0.0.

Last arrow is the learning. We will spend the next twenty minutes inside each of these arrows.

2:10, four steps. This is the heart of the policy. A language model is a function: all the text so far goes in, a probability for every possible next token comes out. The set of those probabilities is the policy.

Step 1: the bars. These probabilities are illustrative, but the shape is real: a few likely tokens and a long tail. A real model chooses among roughly a hundred and fifty thousand tokens at every position.

Step 2: temperature. Low is cautious, always the favourite. High is adventurous. This is the exploration dial from the previous act. Step 3: sample. Same prompt, different answers. That diversity is what lets RL find a better attempt. Step 4: the punchline: training changes these bars. That is all learning is here.

Our student model is a small open model, Qwen3 1.7B, running locally on a laptop.

1:10. The answer is the whole sequence of token choices from the previous slide, a thousand or more, until the model stops or hits the cap.

1:50, four presses. The model's code is untrusted code, and we are about to run it. So it runs in a box.

Press 1, 2, 3: the box is built in layers. The shop app first, then the model's files, then the hidden tests last, so the answer can never overwrite the grader.

Press 4: the rules of the box. No internet, one CPU and 512 MB, the model cannot write to tests or vendor, and the container is thrown away after every run. It is a normal Docker container with the risky Linux powers switched off.

2:00, four presses. The reward is the red or green from the TDD act, turned into a number.

Check 1: the test process finished cleanly, exit code zero. Check 2: the right number of tests ran, all 13 for cart-add. That stops an answer that deletes tests or crashes before they run. Check 3: nothing failed, errored or was skipped.

Press 4: all three hold, the reward is 1.0. Anything else, including garbage output or a timeout, is 0.0. Objective, automatic, repeatable.

2:10, three presses. Real numbers from cart-update: 25 tests, 21 from earlier work, 4 new for this task.

Press 1, all or nothing: only the correct answer is paid. Fair, but a near miss earns the same as doing nothing.

Press 2, share of all tests: sounds kind. But an empty answer already passes the 21 old tests, so doing nothing scores 0.84, the same as my model's real try. The model would learn that doing nothing is fine.

Press 3, share of only the new tests, and the old ones must still pass: empty is 0, half done is 0.5, correct is 1. The reward is a specification. The model will produce whatever it pays for.

2:10, three presses. Two real holes I found in my own gym, before any training.

Press 1: I removed lockForUpdate from checkout, the guard against two buyers taking the last item. Every test still passed, because the tests run one buyer at a time on SQLite. The reward can only punish what the tests check.

Press 2: model code can register a shutdown function that rewrites the test report with fake passes. An unimplemented feature scored 1.0. I reproduced it and documented it with a failing-on-purpose test. It is not fixed yet, and it must be before any real training.

Press 3: the fix direction. The verdict must come from a process the model's code never runs in.

The catch

No passes means no signal. Teach with examples first.

The habit

Read answers, not just scores.

2:00, three presses. For one task we do not take one answer, we take a group, say eight. Sampling is random, so the eight answers differ.

Press 1: today's base model. Eight tries, all 0.0. Every answer looks equally bad, so there is nothing to learn from. That is my real baseline on the Laravel tasks.

Press 2: imagine a slightly better model. Two of eight pass. Now the winners stand out from the losers, and that difference is the learning signal.

Press 3: why a group at all. A 1.0 alone means nothing. It is great if the others failed and ordinary if they all passed. The group gives the comparison.

2:20, three presses. Same eight rewards. The group average is 0.25, two out of eight.

Press 1: the advantage of an answer is how far it sits above or below that average. Winners get a big positive number, losers a small negative one. The real method, GRPO, also divides by the spread of the scores, which is why the numbers are +1.7 and -0.6. You do not need the formula, only the idea.

Press 2: above average, do more of it. Below, do less.

Press 3: the key case. If all eight fail, or all eight pass, every advantage is zero. No signal, no learning. You can click any answer to flip it and watch the bars move.

2:20, three presses. This is the learning itself. Remember from step 3: an answer is a chain of token choices, each with a probability.

Press 1: one choice inside an answer, how to add an item to the cart. Before the update, the model prefers create.

Press 2: the two winning answers chose firstOrNew, the losers chose create. Winners carry +1.7, losers -0.6.

Press 3: after the update, firstOrNew is more likely and create less likely. Illustrative numbers, real mechanism. Each lap is a small nudge, with limits so one lap cannot wreck the model. Only a small adapter is trained, which is what LoRA means, so it fits on modest hardware.

2:10, five presses. Put it together. Press 1: pick a task, sample eight answers. Press 2: run each in the sandbox, two pass, compute advantages. Press 3: nudge the model toward the two winners. Then the next task, thousands of times. These numbers are illustrative: I have not trained yet.

Press 4, the catch, also called the cold-start problem: my base model solves none of the seven Laravel tasks, so every group is all zeros and every advantage is zero. The usual fix: fine-tune on good examples first until some answers pass, then reinforce.

Press 5, the habit: while training, watch the pass rate on held-out tasks and read saved answers. A score can rise while the code gets worse.
