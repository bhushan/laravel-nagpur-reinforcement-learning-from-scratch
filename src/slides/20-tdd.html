Act 1 · Test-driven development

TDD is a loop with a judge in it.

  • Red. Write a test for behaviour that does not exist yet. Watch it fail.
  • Green. Write the smallest code that makes it pass. Nothing clever.
  • Refactor. Clean it up. The test tells you if you broke anything.

The test comes first, so it cannot be bent to fit the code.

Why it works

Three properties make a test a good judge.

Objective

Pass or fail.

No opinions, no mood, no "looks fine to me".

Automatic

Seconds, no human.

Nobody has to read the code to know the verdict.

Repeatable

Same code, same verdict.

Run it a thousand times and it never changes its mind.

Keep these three words

A judge that is objective, automatic and repeatable can score a million attempts without getting tired. That is the entire requirement for a reward.

1:00. Slow down on each card, one sentence each.

Objective: the test does not care about style or effort. Automatic: it runs without a human. Repeatable: no flakiness, or the signal is noise.

Then the bridge sentence: a judge with these three properties can score a million attempts without getting tired. In reinforcement learning we call what the judge hands back a reward. Write the three words in your head: objective, automatic, repeatable.

Aside if asked: flaky tests are poison for exactly this reason. We will see a version of that when a model learns to cheat the judge.
